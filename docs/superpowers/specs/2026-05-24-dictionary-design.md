# Dictionary — curriculum-vocab phrasebook with English-first search

## Goal

A `/dict` page that reads like a dictionary: every curriculum vocabulary entry and every example sentence is displayed up-front (alphabetical by English headword). A search box at the top filters the lists live as the learner types. Each entry shows Japanese characters with romaji ruby always visible above (red), part of speech / pitch / module provenance, English glosses, and example sentences (also with ruby). Built for live-tutor-session lookup: "how do I say X?", "what does Y mean?".

## Non-goals

- No external dictionary data (no JMdict). Corpus is only the curriculum's `module-vocab.json` files.
- No filters by module / POS / tag (corpus too small to need them).
- No fuzzy / typo-tolerant search (corpus too small to need it).
- No audio playback.
- No saved searches / history.
- No new content authoring — the dictionary IS what's in `module-vocab.json`.
- No changes to the existing module pages or `/reader` / `/kana` / `/chart` tools.

## Decisions baked in

1. **Always-on romaji ruby.** Every kana / kanji shown anywhere on the page has romaji ruby above it, in vermilion red. No toggle.
2. **Browse-first.** When the search box is empty, the entire vocabulary is listed alphabetically by primary English gloss — so the page is useful as a dictionary you can scroll, not just a search tool.
3. **Two sections.** "Words" (top) then "Example phrases" (below). Both filter together as the user types.
4. **English-first sort.** Default alphabetic order uses the FIRST English gloss in each entry's `english` list. Ties broken alphabetically by kana.
5. **Substring match, multi-field.** Search matches against a single pre-built `search_text` per entry that concatenates: id, kana, kanji, reading, every English gloss, pos, tags. Case-insensitive.
6. **Romaji input.** If the query contains any ASCII letters, the query is ALSO converted via `wanakana.toHiragana(query)` and substring-matched against the kana field. So typing `watashi` finds `わたし` even when the English gloss is "I, me".
7. **Result cap.** First 80 matches displayed; "more results matched, narrow your search" message if filter exceeded.
8. **Click-through.** Word entries link to `/modules/<slug>/vocab.html#<id>` (the existing per-module vocab page anchor). Example entries link to their parent word's anchor.
9. **Reuses existing romaji libs.** wanakana + kuroshiro + kuroshiro-analyzer-kuromoji, same pinned versions as `tools/reader.html` and `tools/templates/page.html`. Kuroshiro lazy-loads only if any visible entry contains kanji.
10. **Index built at build time.** A flat JSON `public/dict-index.json` is generated by `tools/build_site.py` from all `module-vocab.json` files. Page fetches it once on load.
11. **Solid paper background**, matching every other page in the site.

### Index entry shape

Words:
```json
{
  "type": "word",
  "module_slug": "01-copula-basics",
  "module_num": "01",
  "id": "watashi",
  "kana": "わたし",
  "kanji": null,
  "reading": "わたし",
  "english": "I, me",
  "english_first": "i",
  "english_list": ["I", "me"],
  "pos": "noun",
  "pitch": "heiban",
  "tags": ["pronoun", "self-introduction"],
  "search_text": "watashi わたし わたし i me noun pronoun self-introduction"
}
```

Example sentences (one per parent entry's `example_sentences[]`):
```json
{
  "type": "example",
  "module_slug": "01-copula-basics",
  "module_num": "01",
  "parent_id": "watashi",
  "kana": "わたし は がくせい です。",
  "kanji": null,
  "english": "I am a student.",
  "english_first": "i am a student",
  "search_text": "watashi わたし は がくせい です i am a student"
}
```

`english_first` is lowercased + punctuation-stripped from the first English gloss (for words) or the full English sentence (for examples). Used as the alphabetical sort key.

`search_text` is lowercased and joined with spaces, includes ALL searchable fields.

After the HTML is built, a `rubifyAll()` walk applies ruby to every `.jp` element using the same `splitKanaIntoMorae` / `renderWithWanakana` (and conditionally `renderWithKuroshiro`) helpers as `tools/reader.html`.

### Search logic (in JS)
```js
function filterEntries(query, allEntries) {
  if (!query) return allEntries;
  const q = query.toLowerCase().trim();
  const qKana = /[a-z]/.test(q) ? window.wanakana.toHiragana(q) : null;
  const matches = [];
  for (const e of allEntries) {
    let score = e.search_text.indexOf(q);
    if (score < 0 && qKana) {
      score = (e.kana || "").indexOf(qKana);
    }
    if (score >= 0) matches.push({ entry: e, score });
  }
  matches.sort((a, b) => a.score - b.score);
  return matches.map(m => m.entry);
}
```

Browse-mode (empty query): all entries sorted by `english_first`, then by `kana`.

## Risks

- **Inline JSON growth.** Today ~35 KB; if M02–M12 fill out, could reach ~500 KB inline. Still fine. If it ever becomes a problem we can switch to fetched `dict-index.json`.
- **Romaji input ambiguity** (`ha` → は or ha?). wanakana's `toHiragana` is deterministic Hepburn — fine for our use case (the user types romaji of a Japanese word, not Latin words that happen to look like romaji).
- **Re-rubifying on every filter** would be slow. Mitigation: build ruby HTML once when the entry is first rendered; filtering hides/shows entries (display:none) instead of re-rendering.
- **Anchor links to vocab.html** depend on `vocab.html` existing for that module. It does for M00 + M01; empty modules don't generate vocab pages, so they won't appear in the dictionary corpus either.
